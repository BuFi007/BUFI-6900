# Adversarial pre-Tenderly review — BUFI ERC-6900 v0.7 plugins

**Date:** 2026-09-02  
**Reviewed commit:** `87efb304e0e03ecbfe8b51c2fd93ff067985fc27`  
**Scope:** BUFI's custom `BufiSessionKeyPlugin` v0.7 port and its permission/storage libraries, `BufiEarnModule`, and the new `BufiSessionRecipientHookPlugin`.  
**Explicitly out of scope:** Circle's vendored `UpgradableMSCA`, factory, `PluginManager`, `PluginExecutor`, weighted multisig, AddressBook, and SponsorPaymaster implementations. They were treated only as fixed integration behavior. BUFI's v0.8 Gateway work is also outside this review.

The review used the production-bytecode harnesses in `contracts/test/harness/`, read the defensive suites as the baseline, traced all D1–D9 changes against the pinned Alchemy source, compared the pinned storage layouts, and added 34 adversarial tests under `contracts/test/adversarial/`. The final run was:

```sh
cd contracts && FOUNDRY_OUT=out-codex FOUNDRY_CACHE_PATH=cache-codex forge test --offline --match-path 'test/adversarial/**' -vv
```

Result: **27 passed, 7 failed, 0 skipped (34 total)**. In this suite a test asserts the safe outcome, so the seven failures are intentionally retained evidence that the attack succeeded. `--offline` disables only Forge's remote selector lookup; it was necessary because this host's macOS proxy initialization crashed Forge after compilation in online mode. It does not alter EVM execution.

No Critical or High issue was confirmed. The highest-rated issue is Medium: a non-gas-limited session key may use nonce lane zero and invalidate a pending owner revocation. Six Low issues were confirmed around recipient semantics, non-standard tokens, vault output checks, and dependency misconfiguration. One informational ordering observation and one strict-bundler compatibility question are also recorded.

### Finding detail and exploitability notes

**F-01 — nonce lane collision.** EntryPoint increments nonce before account validation/execution. The plugin checks lane equality at `SessionKeyPermissions.sol:123` only inside `if (sessionKeyData.hasGasLimit)`. The PoC signs an ordinary unrestricted agent transfer with `getNonce(account, 0)`, includes it, and then submits a previously signed owner revocation also using lane zero. The latter is stale and fails, leaving the key installed. This does not forge owner authorization and does not defeat a revoke that lands first. It is nevertheless a realistic mempool race during incident response, and the agent can repeat it while still authorized. The narrow root fix is to apply the existing lane invariant to all session keys.

**F-02/F-03 — the hook enforces syntactic recipients, not eventual destinations.** Direct standard `transfer`, `transferFrom`, ERC-721, ERC-1155, native calls, duplicate batches, and mixed batches behaved safely. The failures occur because `RecipientAddressLib` answers “which address appears in these bytes?” It cannot establish what arbitrary target code ultimately does. An approved spender can always redirect later, and a selector-compatible contract can interpret its arguments differently. These findings do not make an untrusted target magically callable: the target/spender still needs both owner-created AddressBook/access-list authority. The report therefore rates them Low, while changing README finding 3 from “closed” to “closed for direct, semantically standard calls.”

**F-04/F-05 — token behavioral assumptions.** Rebasing the account balance between calls did not reset the stored nominal usage. A zero-value token revert rolled back the pre-execution usage update. The two failures are narrower: actual sender debit may exceed the encoded amount, and low-level EVM success is not equivalent to an ERC-20 boolean success. Generic support for hostile token semantics is impossible without a trust boundary: even `balanceOf` can lie. The safest minimum is an explicit supported-token policy plus SafeERC20-style return handling; actual-delta enforcement can improve behavior for trusted implementations.

**F-06 — vault trust is broader than config immutability.** The two-step approval/deposit transaction is atomic when `deposit` reverts. Reentrant attempts to call `autoEarn` or `changeConfigHash` failed at account validation, and uninstall left shares in the account so owners could redeem them. What did not hold was value/output validation: the adopted vault took 100 USDC and returned/minted no shares, yet `AutoEarnExecuted` was emitted. Because vault adoption is quorum-approved, this is not an untrusted relayer choosing a destination, but it should be explicit that config adoption authorizes all vault behavior, including fees, exchange-rate manipulation, and retained allowance semantics.

**F-07 — generic dependency interfaces do not prove semantics.** Circle correctly rejects missing, short, or not-installed dependency arrays. It cannot infer that an installed `IPlugin` at slot 1 is the weighted owner validator. The crafted `changeConfigHash` calldata places ABI offset `0x40` in the function's first argument while its entire tail decodes as `(Call[], sessionKey)` for the wrongly selected validator. The session signature validates it and the account stores config hash 64. No registered Keccak config is expected at that small value, so the demonstrated consequence is disabling `autoEarn`; it is not vault substitution. Correct `[weighted:1, weighted:0]` wiring passed every route test.

**F-08 — no hash collision.** `keccak256(abi.encode(newConfigs))` is unambiguous for the fixed struct array, and changing vault/order changes the commitment. Constructing two different ABI encodings with the same digest would require a Keccak collision; none was constructed. The sole observation is that the contract trusts callers to sort, so logical set equality is not canonical.

**F-09 — strict-bundler question.** The pinned ERC-7562 text defines associated storage as the account value itself or `keccak(A || x) + n` for one `bytes32 x`. Ordinary mappings such as `_addressBookOf[account]`, `_keyIdCounter[account]`, and `accountConfig[account]` have the expected account-keyed form. `PluginStorageLib` and `AssociatedLinkedListSetLib`, however, deliberately hash longer preimages containing account, batch/prefix, storage key, and sometimes entry. These are the audited ERC-6900 reference-library conventions and Circle's own plugins use the same linked-list library. The README also records a real Circle bundler session-key success, so this is not presented as a confirmed incompatibility with Circle. A different strict tracer may apply the literal definition, which cannot be proven or disproven with Foundry execution alone.

#### Four-plugin composition

One account was configured with Weighted + AddressBook + SessionKey + Earn + RecipientHook. The meaningful partial ordering is constrained: Weighted precedes its three dependents, and AddressBook precedes RecipientHook; SessionKey can be installed on either side of RecipientHook. Tests covered SessionKey-first and Hook-first arrangements plus Hook-first, Session-first, AddressBook-first, and Earn-first cleanup. Weighted uninstall remained blocked until SessionKey, Earn, and AddressBook released their dependency counters. RecipientHook has no declared dependency, so it neither blocks SessionKey/AddressBook uninstall nor leaves a stale dependency slot. AddressBook-first removal made the remaining hook fail closed; SessionKey-first removal left only the hook entries until hook cleanup.

With correct wiring, a session key could not reach `autoEarn`, `changeConfigHash`, `addSessionKey`, `removeSessionKey`, `updateKeyPermissions`, or AddressBook management, directly or through a callback. RecipientHook exposes no account execution/admin selector of its own. The earn relayer could not mutate SessionKey, AddressBook, or Earn config state. No cross-plugin storage collision was observed.

The direct recipient gap is closed for standard native/ERC-20/ERC-721/ERC-1155 calls and every leg of ordinary batches. It is **not** closed for all downstream effects: `approve` delegates a later destination, and an arbitrary allowlisted contract can expose a selector that the decoder interprets as token movement while executing different logic (F-02/F-03). Explicit hook uninstall also reopens the gap by design; no transient unauthorized window appeared without an owner-authorized install/uninstall operation.

#### ERC-4337 / ERC-7562 validation review

No live strict bundler was run locally; the conclusions here are source-level against the pinned ERC-7562 rules.

- **Session `userOpValidationFunction`:** it calls no value-bearing external target, uses ECDSA recovery through an accepted core precompile, and does not use blocked environment opcodes. Time refresh validation returns `validAfter = lastUsed + interval` instead of reading `TIMESTAMP`; actual `block.timestamp` reads occur during execution/reset management. Gas-limited validation writes account-associated plugin storage, which STO-021 permits for an already deployed account if the tracer recognizes the derivation. Ordinary account-root mappings are recognizable; the longer permission/linked-list preimages are the unresolved F-09. For counterfactual deployment, STO-022 additionally depends on a staked factory, but Circle does not install this two-dependency plugin in the account constructor.
- **Recipient `preUserOpValidationHook`:** `_addressBookOf[account]` is an ordinary account-associated mapping. The external AddressBook `STATICCALL` reads the same account's linked-list storage, again subject to the tracer recognizing the extracted associated-list convention. It uses no banned environment opcode or state write. `target.code.length` executes `EXTCODESIZE`; for a no-code target the pinned OP-041 rule rejects the access. Solidity also reverts `InvalidTargetCodeLength`, so this remains fail-closed but a bundler may report a rule violation instead of the contract error. Calls scale as O(number of calls × AddressBook entries) and run before signature verification, so a very large list increases simulation-DoS/reputation exposure even though no authorization bypass follows.
- **Earn:** it supplies no working self `userOpValidationFunction` or pre-userOp hook; those stubs revert. `changeConfigHash` delegates userOp validation to the configured owner plugin, and `autoEarn` is runtime-only. Earn's global owner/relayer/config storage reads therefore do not occur in account-validation simulation. Its execution-time token/vault calls are not ERC-7562 validation accesses.
- **Composition:** every validation-touched custom storage root is intended to be keyed by `msg.sender` account. No BUFI validator reads another account's key or Earn's plugin-global owner/relayer slots. The only cross-contract validation read is RecipientHook into that same account's AddressBook set.

## Severity reassessments of README findings 1–7

1. **Stock Alchemy plugin cannot install on Circle v0.7 — unchanged, Informational/integration status confirmed.** D1/D2 ABI parity inside BUFI's port held, while the original v0.6 `UserOperation`-typed Circle `IPlugin` interface mismatch remains the reason a port is necessary. No new exploit changes the status.

2. **Superseded 2026-08-02 Earn build — unchanged, deployment-blocking status confirmed.** The reviewed build's raw routed `changeConfigHash` works with correct weighted dependencies, while `execute(plugin, …)` still correctly fails `TargetIsPlugin`. F-07 adds a deployment-time requirement: verify the semantic dependency refs, not only array length/interface support.

3. **Recipient gap “closed” by RecipientHook — status changed to partially closed; Low residual risk.** Direct standard calls and ordinary batches are gated correctly. Approve-then-pull and selector-compatible proxy targets demonstrate that the hook cannot guarantee the eventual recipient for every path. The realistic precondition is owner trust in the spender/proxy, which keeps severity Low, but documentation should not claim universal closure.

4. **Weighted owners cannot act at runtime — core finding confirmed as-is; configuration guard strengthened.** Correct slot 0 → weighted id 1 and slot 1 → weighted id 0 wiring held for Session and Earn management. F-07 shows that Circle's dependency validation is structural, not semantic: a wrong installed `IPlugin` in slot 1 can validate a selector with attacker-controlled ABI. Exact post-install loupe checks should be mandatory.

5. **Gas-limited keys must use their address as nonce key — severity/status broadened to Medium liveness risk.** The existing rule and public-reset behavior held for gas-limited keys. Non-gas-limited keys have no lane restriction and can consume owner lane zero, invalidating pending revoke/update operations (F-01). The same address-lane rule should cover every session key.

6. **ERC-20 budget is execution-phase — core status confirmed, with two Low semantic qualifications.** Atomic rollback and standard-token over-limit behavior held. F-04 shows the budget is the calldata amount, not necessarily actual account debit; F-05 shows an ERC-20 `false` return is treated as successful and consumes budget. README should say “nominal standard-token budget” unless these cases are fixed.

7. **GatewayExecutionModule v0.8 depositor identity — not independently reassessed because it is outside this review's explicit v0.7 custom-plugin scope.** Nothing in the reviewed Session/Earn/Recipient code changes its stated status or severity. The existing README conclusion is retained, not re-verified here.

## What Tenderly would add

Foundry fully resolved deterministic authorization, storage-state, reentrancy, batching, time-boundary, uninstall, and local EntryPoint arithmetic cases. The following items need a live vnet, real bundler policy, or forked protocol state:

1. **Strict ERC-7562 bundler simulation.** Send direct-transfer, empty-selector, gas-refresh, hook-batch, no-code-target, and wrong-signature Session userOps through a bundler that exposes validation traces. This resolves F-09 by showing whether its tracer classifies the three-/four-word `PluginStorageLib` and associated linked-list preimages as account-associated under STO-021. It also confirms how the RecipientHook's AddressBook `STATICCALL`, no-code `EXTCODESIZE` branch under OP-041, and O(calls × recipients) pre-signature work affect admission, second validation, account reputation, and canonical-mempool propagation. Forge can execute the bytecode but does not enforce bundler opcode/storage attribution.

2. **A real v0.7 paymaster.** The local EntryPoint/mocked paymaster proved D6's arithmetic exactly: verification, call, preverification, paymaster verification, and postOp limits were each charged once, and actual gas was below required prefund. A vnet should add real paymaster validation data, sponsorship expiry/signature failures, nontrivial `postOp`, unused-gas penalties, and the bundler's estimation caps. This determines whether maximum-prefund policy causes practical false rejection or whether any real paymaster packing/estimation path differs from the local static fields. It cannot create an arithmetic undercharge in the tested formula, but it can expose admission and refund integration behavior.

3. **Mainnet-forked Morpho Vault V2 behavior (`docs/EARN-MORPHO.md`).** Manipulate vault exchange rate, donation/rounding, fee state, deposit caps/pauses, asset balance, and share price immediately before `autoEarn`; compare `previewDeposit`, returned shares, actual share delta, and retained allowance. Then uninstall with shares outstanding and redeem through the real vault. The local malicious vault confirms that zero/bogus output is unchecked (F-06), but only forked Morpho state can determine whether a realistic minimum deposit, fee, or manipulated share-price condition reaches zero/excessively low shares and whether its real revert/allowance behavior is atomic as assumed.

4. **Public-mempool ordering for incident response.** Reproduce F-01 with an owner revocation and agent lane-zero userOp simultaneously visible to a bundler, including replacement/priority behavior and repeated agent submissions. Local chain ordering proves the state transition; a vnet measures whether the production SDK/bundler makes the race practical and validates the operational mitigation of a distinct owner management lane.

No local scenario remained unconstructed for access-list modes, batch atomicity, plugin reentrancy, D7 codeless installation, uninstall/dependency cleanup, relayer revocation, or Circle validation-data packing. Their adversarial attempts are executable in the added suites and held.
